# zygisk-extdensity — External Display Tablet Fix

A standalone **Magisk Zygisk** module that makes selected apps render their **tablet** layout on the
TB323FU's external monitor. It is the production form of the fix written up in the repository root
`README.md` (*Fixed: apps render a phone layout on the external monitor*); the control UI is the
**ZUI Tweaks** app in this same repository, not LSPosed.

The built `.so` is snapshotted into `../magisk/zygisk_extdensity/`, which the app packs into its own
assets and installs. Nothing in the app's build runs the NDK — you only come in here when the module
itself changes.

## The bug it fixes

On the external monitor, an app's `getSystemService(WINDOW).getDefaultDisplay().getRealMetrics()`
returns the monitor's pixel size (2560×1440) with the **internal** panel's density (440 dpi), so any
`min(px)/density ≥ 600` tablet check (react-native-device-info, etc.) computes `1440/2.75 = 523.6` →
phone. The monitor's real density is 213; every other path (`Configuration`, `wm density -d 2`, the
activity context) already reports 213 — only this legacy call is wrong.

## What it does

Hooks `android.view.Display.getRealMetrics`/`getMetrics` in the app process and, **only** when the
returned metrics carry the monitor's size at a foreign (internal) density, rewrites the density to the
monitor's own value (read once from the external `Display`). A no-op on every other surface.

## Design

- **Global module, per-app allowlist.** Zygisk injects into every process, but the module acts only on
  packages the user selected. Channel: a boolean prop `persist.zui.extdensity.<fnv1a(pkg)>=1`, set by
  the ZUI Tweaks app via root `resetprop`, read by the module in `postAppSpecialize`. Changing the
  selection applies on that app's next start — **no reboot**. The Kotlin `ExtDensityTargets.propName`
  (`../app/src/main/java/io/laelaps/zuitweaks/settings/ExtDensityTargets.kt`) and the C++ `propName()`
  in `module.cpp` compute the **same** FNV-1a and must stay in sync.
- **Hook stack (one self-contained `.so`).** LSPlant (ART Java hook, built from source, C++23 modules,
  static) + **Dobby** inline backend (vvb2060 prefab, thread-safe) + **xDL** symbol resolver, all
  `c++_static`. A tiny **embedded dex** (`Hooker.java` → `hooker_dex.h`) holds the Java callback, loaded
  via `InMemoryDexClassLoader`.
- **Safety.** Hooks only after `sys.boot_completed` (boot processes never touched, so it can't break the
  boot); no `postServerSpecialize` (system_server untouched). See `RECOVERY.md`.

## Layout

```
zygmod/                 Gradle project that builds the Zygisk .so (AGP + externalNativeBuild/CMake)
  src/main/cpp/
    module.cpp          Zygisk module: postAppSpecialize gate + LSPlant init + getRealMetrics hook
    zygisk.hpp          the official Zygisk module API header, vendored and PINNED to API v4
    hooker_dex.h        embedded dex bytes (generated by make_dex.py; committed)
    CMakeLists.txt      links deps/{LSPlant,xDL} + the dobby prefab, static
deps/                   LSPlant (+ its dex_builder / parallel_hashmap submodules) and xDL — cloned,
                        not committed; see Build below
hooker/…/Hooker.java    the Java callback (density correction); compiled to dex by make_dex.py
make_dex.py             javac + d8 Hooker.java → hooker_dex.h
RECOVERY.md             what to do if a build breaks the boot
```

## Build

Clone the two third-party sources once (they are gitignored):

```sh
mkdir -p deps && cd deps
git clone --depth 1 https://github.com/LSPosed/LSPlant.git
git -C LSPlant submodule update --init --depth 1 --recursive \
    lsplant/src/main/jni/external/dex_builder
git clone --depth 1 https://github.com/hexhacking/xDL.git
```

Clone LSPlant **without** `--recursive`: two of its submodules are test-only and use `git@` URLs, so a
recursive clone aborts before it reaches `dex_builder`, which is the one that is actually needed.
Dobby comes from Maven (`io.github.vvb2060.ndk:dobby`), not from a clone.

Then, from the repository root:

```sh
# 1. (only if Hooker.java changed) regenerate the embedded dex
python zygisk-extdensity/make_dex.py
# 2. build the .so
./gradlew -p zygisk-extdensity :zygmod:assembleRelease
# 3. re-snapshot it where the app picks it up
cp zygisk-extdensity/zygmod/build/intermediates/stripped_native_libs/release/\
stripReleaseDebugSymbols/out/lib/arm64-v8a/libzygisk_extdensity.so \
   magisk/zygisk_extdensity/zygisk/arm64-v8a.so
```

Bump `versionCode` in `../magisk/zygisk_extdensity/module.prop` when you re-snapshot, so Magisk sees
an update. Then rebuild the app: the zip is packed from `magisk/zygisk_extdensity/` into the APK
(`packExtDensityModule`), and **ZUI Tweaks → Misc** installs it. One reboot to activate — Zygisk only
loads modules at zygote start. App selection after that is reboot-free.

### Verifying a build actually loaded

```sh
adb shell su -c 'am force-stop <allowlisted.pkg>'   # required: the log below is printed once,
adb logcat -c                                       # at process start
adb shell monkey -p <allowlisted.pkg> -c android.intent.category.LAUNCHER 1
adb logcat -d -s ExtDensityZ:V
```

Expect `selected app … installing external-display fix` / `lsplant::Init -> 1` / `hooked in …`.
**Silence means the module did not load** — most likely the Zygisk API version is newer than the
installed Magisk supports (see the note at the top of `zygisk.hpp`). Two traps make silence easy to
misread: relaunching *without* the force-stop reuses a process that was specialized before
`logcat -c`, and Zygisk unmaps the module after specialization, so the `.so` being absent from
`/proc/<pid>/maps` is normal and proves nothing.

## Notes / dead ends

- Zygisk **companion** (`connectCompanion`) returns -1 for every app on this Magisk 30.7 → property
  channel instead. The app's own files-dir is unreadable cross-domain (SELinux `app_data_file`) → props.
- **And64InlineHook** is thread-unsafe and crashed the multi-threaded ZUI launcher; **Dobby** fixed it.
- **Dobby from jmpews/master** won't build for Android arm64 (`@PAGEOFF` Mach-O asm); the vvb2060
  prefab static-links cleanly into the one `.so`.
- Requires **arm64** targets only (the device's apps of interest are 64-bit); Magisk logs a harmless
  `openat 'zygisk/armeabi-v7a.so': No such file or directory` at install.
